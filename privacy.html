SRC-D2 // Privacy Protocol

OPERATOR-FIRST · LOCAL-FIRST · NO TELEMETRY

This document describes what the suite does with your data. It is written to be checkable: every claim here corresponds to something in the code, and where a protection is partial or a risk is real, it is named as such rather than smoothed over.

THE SHORT VERSION The network killswitch (ᚾ) is engaged at every launch, and until you release it the dashboard talks to nothing but the server it was loaded from. Released, it reaches the few services named in section III, each through one gate the browser also enforces — and the weather, alerts and supporter check only after you switch them on, under a callsign. Provider keys are sealed on this device and never shown, printed or exported (section IV). There is no analytics endpoint, no crash reporter, no account, and no server that holds your work. The suite has nowhere to phone home to.

I. Local Data Persistence (The Vault)

Projects, incidents, scratchpad buffers, the track and clip libraries, the design library, saved rigs, captured arrangements and the authority record all live in localStorage, sessionStorage and IndexedDB on the device that created them.

  • Guest sessions use sessionStorage under their own namespace and are gone when the tab closes.
  • Callsign sessions use localStorage under a namespace derived from the callsign.
  • Audio and design blobs live in IndexedDB, because a few seconds of audio does not fit in localStorage and never will.

Clearing your browser's site data erases all of it. There is no copy anywhere else, which is the point and also the risk: if you have not exported it, it is not backed up.

What a library entry actually holds

A track entry does not store audio by default. It holds metadata and one of three things: nothing, a fingerprint (filename, size and modified time) for re-pointing at a file you pick again, or the bytes themselves under a conservative ceiling. The panel says which, per entry, because an entry that only names a track and one that can deliver audio look identical until you try to use one.

II. Hardware & Sensor Processing

Where the suite reads a sensor, it reads it locally and does not retain the raw signal. Analysis happens in the page or in a worklet; nothing is uploaded for processing.

Connected instruments (MIDI)

DΛTΛ_WΞΛVΞ enumerates MIDI devices through the browser's Web MIDI interface. That returns each device's manufacturer-supplied name — "Keystation 88 MIDI 1", "LPK25". This is hardware identification rather than personal data, but it is identifying in the sense that a given rig is recognisable across sessions.

Note data is read continuously while a controller is routed, and is used for routing, for the tempo readout, and for capture when a take is armed. There is no network call anywhere in the MIDI path.

A saved rig stores those device names in a project. If you share a rig file, the instrument names go with it. Nothing else about the device does.

Bluetooth (BLE Hardware Auditor)

Scanning is user-initiated and returns device names and advertised service identifiers. That data stays in the panel and in the local registry you choose to keep. The suite does not connect to a device without an explicit action and does not transmit what it finds.

Device profile (display tier)

The dashboard draws itself more cheaply on hardware that needs it: blur, scanlines and animated glows cost real frames on an older phone. It does not inspect the device to decide this. At load it reads the viewport — its size, its orientation, and whether the main pointer is a mouse, the same media queries any stylesheet asks — and nothing about the hardware: no user-agent parsing, no graphics probe. It starts on a baseline and stays there until you say otherwise.

Saying otherwise happens in one place, the Hardware Auditor, and only when you tap ⊕ READ PROFILE. That tap reads:

  • the operating-system family and, where the browser reports one, the device model — from the browser's platform hints and the user-agent string;
  • the graphics renderer name, through one WebGL context that is released as soon as it has been asked;
  • the screen size in density-independent pixels, and the refresh rate, measured over about half a second.

What it found is shown to you before anything is done with it. The two fields the outcome depends on, OS and GPU class, can be corrected by hand: a browser that masks its graphics hardware reports a generic renderer, and you know what you are holding. The profile exists in memory only, and closing the auditor discards it.

If you tap ⌁ SHARE, the dashboard takes the OS and the GPU class, looks up one of four display tiers in a fixed table, and keeps that one value — t1, t2 or t3 — in localStorage under srcd.tier. The profile is dropped in the same step. The model name, the renderer string, the screen size and the refresh rate are never written to storage, and there is no network call anywhere in this path.

↺ FORGET, in the same panel, removes the key and returns the dashboard to its baseline at once, without a reload. Clearing site data does the same. A tier changes what things cost and how large they are, never what is there: no control, field or feature is absent on a lower one.

WHAT THE STORED VALUE STILL SAYS
  • The tier is coarse on purpose — older Android phone, newer Android phone, desktop — but it is a statement about your device, and anything that can read this origin's storage can read it.
  • It is kept once per browser, outside any callsign namespace, because it describes the device and not the operator. Every session on this browser gets the same tier, Guest included.
  • Reading a profile creates a WebGL context for a moment. A privacy tool that reports such things may report this one. It happens on that tap and at no other time.

III. The Network: One Switch, One Way Out

STATED PLAINLY There is no telemetry. No usage analytics, no error reporting, no heartbeat, no remote configuration. The suite is a set of local files.

Every launch starts severed

The network killswitch (ᚾ) is engaged every time the dashboard opens. Logging in, loading a key image and recalling a callsign never release it. Only a tap on ᚾ does, and the dashboard asks the browser whether a person really made that tap, so no script can release it on its own. Anything may engage it again: you, or code that wants to be sure nothing goes out. While it is engaged, the dashboard contacts no other site. That has been tested over a whole session: login, the vault splash, Net Sentry left running, both documents, the code sandbox, a preview of a page that names remote files, and idle time — and, since the key vault arrived, a key typed in and switched on, every feed refreshed, a place searched, a supporter check, the debrief and the stream view. The one exception is a Python runtime already loaded during an earlier release: code you run in it can still ask Pyodide's own folder for a package (below).

One way out, and a lock behind it

Every online request goes through one function, NetGate, which holds a short, fixed list of services. It checks, in order: the switch; that the device has a link; that the service is on the list and enabled; that the address, path and method are on that service's own list; and, once a reply arrives, that it is the size and type that service sends. The first check that fails ends the request. Each request or refusal leaves one line in the Net Sentry log: which service, the outcome, the time and the size. The full address, its query string and the headers are never logged.

Behind that, the page carries a Content-Security-Policy naming the same hosts. The browser enforces it, and nothing in the page can loosen it. A request to any other host is refused by the browser, even if some code tried to step around NetGate. The attempt is logged and raises a notice. Frames the dashboard writes for itself (the preview and the code runners) inherit the same list. Adding a service means editing both lists, and the dashboard checks at launch that the two agree.

What can go online, once ᚾ is released

  • Public IP lookup. The ⌖ button in Net Sentry asks api.ipify.org for your public address, once per tap. That service sees your IP address, which is the answer it sends back. In forced-offline mode the button does not ask.
  • The Python runtime. The first time you run Python in the Ω sandbox, it downloads Pyodide (~10MB) from one pinned release folder on cdn.jsdelivr.net, which sees that request. Once loaded, Python runs offline. Engaging ᚾ while it is still downloading cuts the download off. The runtime's frame can reach that one folder and nothing else. Once the runtime is in, Python code you run can still ask that same folder for a package the release ships (that is how Pyodide's loadPackage works), whether or not ᚾ is engaged. Plain Python asks for nothing.
  • Pages you preview. The scratchpad preview renders the HTML you give it. With ᚾ engaged the preview is sealed: it loads nothing remote, and the sentry lists what it refused. With ᚾ released, the images, stylesheets, fonts and scripts that page names are loaded from wherever it names them. Those are that page's own requests, and the sites they point at see them. Its fetch() calls can still reach only the hosts on the dashboard's list, and it cannot be sent to another site.

These four go further only when you switch them on, logged in with a callsign (a Guest session has no switches to turn):

  • Weather, keyless. api.open-meteo.com, once a day: on the first release of a local calendar day, and never within six hours of the last success, so a release at 23:59 and another at 00:01 make one request. It sends your location rounded to two decimal places (about a kilometre) and sees your IP address. Open-Meteo's free service is for non-commercial use, and its data is credited wherever it is shown (CC BY 4.0).
  • Weather with your key. api.openweathermap.org, on the same schedule, when an OpenWeatherMap key is sealed in the vault and switched ON; if it fails, the keyless source above is asked instead. OpenWeatherMap takes its key only in the address (?appid=), so the key is in that one request — sent with no referrer, to that host only, and visible in the browser's own developer tools on this device. It appears nowhere else.
  • Place search. geocoding-api.open-meteo.com, only when you press SEARCH: it sends the name you typed. USE THIS DEVICE asks the browser for your position instead (the browser asks your permission) and sends nothing.
  • Weather alerts. api.weather.gov, the US National Weather Service, about every 45 minutes while the dashboard is open and ᚾ is released, with the same rounded location. It covers the United States only.

The weather and alert feeds are counted per callsign: a daily cap, a cooldown on the refresh button, and a wait when a service answers "too many requests" (as long as it asks, when the browser can read that; fifteen minutes when it cannot). The place search runs only when you press SEARCH, one search at a time and at least a second and a half apart. A reply is read for named fields only — a temperature, a condition, an alert's headline — each checked for type and length; anything else in it is discarded, and text is only ever shown as text.

What does not go online

  • Display fonts. Michroma and Space Mono ship inside the dashboard file itself, under the SIL Open Font License, and are drawn from there at every launch, online or not. No font is requested from anywhere, and Google Fonts is not contacted at all. Before this build the dashboard asked Google Fonts for them at every launch, whatever the switch said.
  • Rust and C++ are not run remotely in this build, and nothing is sent. They used the public Piston service, which closed to anonymous use on 2026-02-15. RUN now says so, along with how to point the sandbox at a Piston you host yourself.
  • The Raspberry Pi telemetry poll in Net Sentry is in the code, disabled, and its address is not on the browser's list.
  • Timestamp requests are saved as .tsq files. You submit them to the authority yourself, and the dashboard contacts none.
  • This page and the changelog carry policies of their own that admit nothing remote. The changelog gets its fonts from the dashboard rather than from Google.
  • News feeds are not configured in this build: no feed's address is on either list. Mock data shows sample headlines instead.
  • Claude and Grok keys can be sealed in the vault, but nothing is sent to either service in this build. Sending arrives with the AI preview, behind its own confirmation.
  • The supporter check (section IV) has no creator account or RPC service configured in this build, so it reads nothing from any network. In mock mode it runs against a built-in mock.
  • The login debrief and the stream view read only what is already on the device: the feeds' cache and the attachment you opened.

Everything else (JavaScript, CSS and HTML checking, audio rendering, image classification, provenance writing, the arrangement scheduler) runs locally with no network path at all.

Reachability checks

To show an honest LINK status, the dashboard checks that it can reach the server it was loaded from. It sends a small request to /__srcd2_connectivity_probe every five seconds and another every five minutes to notice a captive portal. While Net Sentry is open it also requests /favicon.ico about once a second to measure latency. These go only to the server that served the dashboard and carry nothing but a timestamp to defeat caching. They are not online services, and they run whether ᚾ is engaged or not. Opened from your own machine (localhost), they never leave it. Opened from a web host, that host sees them the way it sees every page load.

Secrets are never printed and never exported

Every notice and log line passes through a scrubber before it is shown, and so does every console message once there is anything to hide (on a device with a device lock, from the first line). The scrubber removes the device secret, every provider key in the vault (which it knows by a fingerprint, not by the key: section IV), an operator glyph long enough to be one, and anything shaped like an API key or a key in an address. An export (a backup, a scratchpad tab, the sentry log, a launch packet, the SDAP logs, a provenance file, a timestamp request, a sealed build file, or the two copy buttons that carry the same content) that contains the device secret or a vault key is refused, not altered — and stays refused after the vault locks. Nothing is written, and the notice says why. This holds for plaintext exports in forced-offline mode as much as for encrypted ones, which are checked before they are sealed. A glyph is scrubbed from what is printed but never blocks an export, because you may have written yours into a note on purpose.

IV. Keys, Feeds and the Debrief

Everything in this section belongs to a callsign session. A Guest session has no vault, no feed switches and no debrief, and logging out to Guest locks the vault and closes the rest.

The key vault (hold ᛸ in the SRC menu)

  • Pasted once, then sealed. A key is typed or pasted into the vault panel, which takes it straight out of the keystroke or the paste. The field itself never holds it, and the panel never shows it again. Afterwards it can name the key (which provider, when it was sealed, a four-character fingerprint) but cannot display it.
  • Encrypted on this device. Each key is stored with AES-GCM under a random vault key, and the vault key is itself stored encrypted under the key your callsign login derives. Every record is bound to its callsign and provider, so one cannot be decrypted as another. The records live in IndexedDB under the srcd2_kv_ prefix, which no export reads.
  • Plain only in memory, only while unlocked. A key is decrypted at login and dropped again when the vault locks: the LOCK button, logging out, no input for the idle limit (15 minutes unless you change it), the tab hidden past its grace (2 minutes unless you change it, measured when you come back, because a phone freezes background tabs), or PANIC. A call still in flight with a key is cut off by the lock. This has been tested by searching the page's whole memory for a key: present while unlocked, gone after every kind of lock.
  • Used in one place. Only the network gate can read a key, at the moment it sends to that key's own service; nothing else in the page has a way to ask for it. A key is never printed, and an export that contains one is refused, including in forced-offline mode.
  • Turned on by you. A sealed key does nothing until you switch it ON. Claude and Grok keys can be stored now; nothing is sent to those services in this build.
WHAT THE VAULT CANNOT DO
  • On a device that remembers your glyph, or for a device-locked callsign, logging in again takes only the callsign. There the lock is a speed bump for someone holding the unlocked phone, not a wall. The real limits are each provider's spend cap and your ability to revoke the key.
  • OpenWeatherMap's key travels in the request address. The browser's own developer tools on this device can show it.
  • A key that was pasted stays on the clipboard until something replaces it. The panel has a CLEAR CLIPBOARD button for that.

The ledger

For each callsign, the dashboard keeps a small encrypted record, under the same login key: how many calls each service has had today, when each may be called again, the last good reply (only the fields it read from it), and your settings for this section, meaning which feeds are on, mock data, the lock timings, the debrief and the location. The location is kept rounded to two decimal places. It is sent only to the weather and alert services you switch on.

Mock data

With mock data on, every feed is answered by built-in samples shaped like the real services, through the same gate, counts and cache. Nothing leaves the device, and every sample says MOCK wherever it appears.

The login debrief

When you log in with a callsign, what the feeds already cached can rain down the screen under your callsign: weather, alerts and headlines as falling characters. Tap one and its text scrolls up toward a vanishing point; tap away, press Esc or CONTINUE, and the dashboard appears at once. It shows only what is cached, it never fetches anything for the occasion, and with nothing cached it does not run. AUTO plays two passes on the first login of a day and one after that, SHORT plays one quick pass, and OFF turns it off. With reduced motion asked for in your system settings, the same items are shown as a still list.

The stream view (ᛚ in the attachment viewer)

The same rain and scroll can show an attachment's own text, cut at its sections and functions so you can tap one to read it. It reads the text you opened, on this device, and sends nothing.

The supporter check (Access Protocol)

A creator can offer community content to people who stake toward them through Access Protocol. No creator account is set in this build, so nothing is gated and the check reads nothing. When a creator configures it:

  • you enter a Solana wallet address, which is public information. Nothing is signed and no wallet is connected; the dashboard cannot move anything;
  • on a release of ᚾ the dashboard reads two accounts from a Solana RPC service: your stake toward that creator, and the creator's pool. That service sees the address and your IP address;
  • the answer is kept, encrypted, for 7 days and honoured for 7 more while offline;
  • it is a courtesy lock on community content only. The dashboard itself is never behind it, and it proves nothing about who is holding the phone. An App Store build leaves it unconfigured, because Apple does not allow a crypto holding to unlock app features.

PANIC

Two taps on PANIC in the vault panel, within four seconds: ᚾ is engaged (cutting off anything in flight), every key in memory is dropped, and the vault and the ledger are deleted from this device for every callsign, with the cached feeds, counts, settings and supporter answer in them. Your projects, incidents and other work are not touched. After a panic, revoke each key at its provider: a key that was ever on a device that needed a panic button is a key to replace.

V. The Bridge Between Apps

ØMNI_FRΛMΞ, SHΛDΞPRØØF, SRC-VRT and ØMNI CΛST run on separate origins. STRΛTΛ, when ØMNI's glyph is pointed at its port, takes ØMNI's place in the registry and has exactly ØMNI's permissions. The browser keeps them apart by default. The only channel between them is postMessage, which this dashboard mediates, and every reply goes only to the origin that asked.

Every message is checked twice. The origin says which app is speaking; a per-app verb list says whether that app may say this particular thing. Being reachable is not permission.

  • SHΛDΞPRØØF may ask for the track library and cannot write to it.
  • SRC-VRT may push a finished render and cannot read the library at all.
  • ØMNI CΛST, which renders third-party creative, is sandboxed without same-origin access: it can receive and cannot send.
  • ØMNI_FRΛMΞ may ask for its racks: the module pages attached to rack projects and their SoundFont files cross when it asks, or when you press PUSH. STRΛTΛ may ask for the module pages and SoundFonts of every project, and receives them again when a save while it is open changes one of them, or the name of a project that holds them; any other save sends nothing. Each module page passes the same admission, VΞILPØINT and probe checks on the way out.

Audio is pulled one track at a time when a specific track is requested, never pushed with the library. What crosses is what you curated, and only to an app that asked for it; nothing crosses to a host that is not in the registry.

Panels that report a threat

The preview sentry posts its findings to the dashboard. That listener verifies the message came from a frame this page created, by window reference. Without that check, any page could have raised a fake alert — not code execution, but security-UI spoofing, which matters because a fake alarm teaches an operator to distrust a real one.

VI. The Authority Record

The authority record holds artist name, writers, producers, publisher, master owner, year and ISRC. This is identity and rights data and is treated as such.

  • Off by default. Until you engage it, nothing is stamped into any file, and a bounce taken while it is disengaged records that it carries no claim rather than a half-filled one.
  • When engaged, these fields are written into the files themselves — a WAV metadata chunk, a provenance XML, a video marquee. That is the point of the record, and it means those files carry your name wherever they go. The suite does not send them anywhere; you do.
DECLARED, NOT VERIFIED Every field is asserted by the operator and proved by nothing. No file written by this suite should be read as evidence of ownership. An ISRC is shape-checked and never generated — an ISRC belongs to a registrant, and a fabricated one would collide with a real recording somewhere. Blank is a correct answer.

VII. Clipboard and the Launch Packet

Several panels offer one-tap copy — a staged post, a provenance report, a flagged caption. These write to the system clipboard on an explicit tap and never read from it. The clipboard is shared across every app on the device, so anything copied is available to whatever you paste into next. That is how clipboards work everywhere; it is noted because a panel that copies without saying so is a panel that surprises people.

The launch packet names a lead developer

The SDAP prompt payload carries a >>> COMMANDER: line: your callsign, or GUEST_OPERATOR as a guest. It goes wherever you paste or send the packet, an AI service included. Tap the name in the preview to write another one over it, or switch its rail off and the line is left out. The rails are kept per project, on this device.

VIII. What VΞILPØINT Checks Before Something Leaves

Content passing between apps or heading for a platform is inspected first. Two policies, and they are not the same.

Security governs what crosses between apps: code that builds itself from strings, credentials, private keys, calls to unregistered hosts. Objective and technical.

Broadcast governs what goes out to a platform, and deliberately checks only things that are checkable and that you would want back: a leaked token, a phone number, a street address, a link shortener platforms down-rank.

WHAT IT DOES NOT DO It does not moralise about language. Profanity in a lyric is not a finding. Dark subject matter is not a finding. A word-list tone detector would fire on most of the music ever written, would be safety theatre rather than safety, and would teach you to ignore the panel within a day. The narrow exception is slurs, and even that only ever warns — context is the whole question and a pattern match cannot see it.

For imagery the check defers to the on-device classifier SHΛDΞPRØØF already carries. No image is uploaded for analysis; classification runs locally.

A block stops; everything else asks; a clean scan does not interrupt at all. A gate that halts on a maybe trains people to click through without reading, and then it is stopping nothing.

IX. Operator Autonomy

  • Export everything, any time. Projects, arrangements, rigs and provenance are plain text or standard formats — not a proprietary container you need this app to open. A build file sealed with ⤓ is the same encrypted envelope a backup uses, or plain JSON when there is no key to seal it with.
  • NØIR neutralises the interface for use in public without changing what is stored.
  • The network killswitch (ᚾ) is engaged at every launch, blocks everything in section III, and is released only by your tap.
  • Every online feature is opt-in and reversible. Feeds are switched on one by one and off again from the same panel; a key can be switched off or forgotten; the debrief can be turned off; PANIC removes all of it at once.
  • Delete means delete. Removing a library entry deletes its stored blob, not just the row.

X. What This Protocol Does Not Cover

HONEST LIMITS
  • Files you export and share carry whatever you put in them, including authority fields and rig device names.
  • Once ᚾ is released, the services in section III see what any web request shows: your IP address and your browser. ipify sees that each time you tap ⌖, and jsDelivr when Python first loads — and, released or not, whenever Python you run asks the loaded runtime for a package. The weather and alert services you switch on also see your rounded location; the place search sees the name you typed; OpenWeatherMap sees your key, which is how it knows who is asking.
  • Open-Meteo's free service is licensed for non-commercial use. A commercial build should use OpenWeatherMap with your own key, or Open-Meteo's paid service.
  • The killswitch and the browser policy govern the dashboard and the frames it writes. The creator tools (ØMNI_FRΛMΞ and its siblings) load from their own local servers into frames of their own, and what they fetch is decided by their own files, not by ᚾ.
  • Errors the browser reports by itself, such as an uncaught exception in the developer console, are printed by the browser rather than the dashboard and are not scrubbed. They stay on the device.
  • A browser extension with page access can read anything on the page. No web application can defend against that, and one claiming otherwise is misinforming you.
  • Local storage is not encrypted against someone with the unlocked device in hand. The key vault and the ledger are encrypted under your login, but a login that a device remembers can be repeated by whoever holds that device.
